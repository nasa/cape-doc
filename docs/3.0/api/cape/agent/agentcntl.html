cape.agent.agentcntl: Controller class for CAPE agent¶

This module provdes the class AgentCntl which serves as an object-oriented interface to the CAPE agentic capability and interface. Most of the actual agent loop, including passing user responses on to an external LLM and processing the results, is implemented by methods of AgentCntl.

The module-level list EDIT_FILE_ALLOW_LIST is a registry of POSIX-style file names, relative to the folder in which the agent is launched, that skills may append to at run time (e.g. the fix-json skill registers the file the user asked to repair). The cape.agent.skills.fileedit module merges these names into its edit allow-list in addition to its own static patterns and the files provided by cape.cfdx.cntl.Cntl.get_edit_allowlist().

class cape.agent.agentcntl.AgentCntl(fname: str | None = None)¶

Controller class for the CAPE agentic interface

This class implements the agent loop behind cape --agentic: reading user input, passing messages to an external LLM server, and processing any tool calls in its response. The tools and skills exposed to the LLM are filtered based on the options for the model in use (see cape.agent.options); user skills are discovered from the folder in which the agent is launched (see cape.agent.skills).

Call:
>>> cntl = AgentCntl(fname=None)

Run one pass of model with multi-round tool calling

Run one user turn with up to MaxToolCallLoops rounds of tool calls. This allows the agent to chain tool calls, e.g., calling cape_find() followed by cape_c() with the results from the first call.

cape.agent.agentcntl.show_reasoning(message, framed: bool = True) → bool¶

Display post-response reasoning content when available

This uses the nonstandard reasoning field exposed by current vLLM servers, with reasoning_content as a fallback for older compatible servers. The OpenAI Python client keeps unknown response fields as model extras, so getattr() works even when the installed SDK does not declare either field.
